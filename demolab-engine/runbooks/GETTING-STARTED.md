# Runbook: Getting started

Triggers: **"how do I get started"**, "help me set up", "onboard me", "walk me through this repo". Goal: demo running locally, the user understands the loop, and they've published their *own* first experiment.

## Decisions the agent surfaces

Onboarding is a conversation, not an interrogation. **Hard-gate on only these** — ask directly and wait: install the toolchain, demo-or-clean, stack, clear the demo, publish online, repo public/private, and (last) what to compute. Everything else is **offer-with-a-default** — state the default, let the user redirect, move on. Gather the branding fields in **one pass**, not one prompt each. Bracketed `[n]` points at the step where each decision lands.

**Order matters.** Settle the foundational choices before building anything: **stack → branding → (verify the scaffold builds) → first experiment.** The stack choice changes *what gets scaffolded*, so it comes first; branding (`demolab.yaml`) next; and **don't ask what to compute until the tree is scaffolded and `task build` is green** — a first experiment on a half-set-up tree just compounds problems.

**Must-ask** (destructive, installs software, or unguessable):
- **Install missing toolchain?** `uv`/`typst`/`go-task` — default yes. `[0]`
- **Learn from the worked demo, or start clean?** `task add-demo-content` vs bare `task scaffold` — default demo; "clean" skips the loop walkthrough (jump to step 3). `[2]`
- **Stack?** Python (default, `uv`), or MATLAB/Julia/R/Octave (see `MIGRATE-STACK.md`). **Ask early and explicitly** — it's foundational, more work off-Python, and far better surfaced now than discovered mid-build. `[3]`
- **What do you want to compute?** open-ended, required, no default — but **only after the scaffold is verified** (step 5). `[6]`
- **Clear the demo content?** `task clear-demo-content`, only *after* their own experiment works — default yes. `[7]`
- **Publish online?** default yes; if no, stop after a local build — everything still works. `[8]`
- **Public or private repo?** default public. Pages on a *private* repo needs a paid GitHub plan — say so. `[8]`

**Offer-with-a-default** (state it, don't block):
- **Branding** (`demolab.yaml`, one pass): site name (default "demolab"), one-line tagline (default none), book/PDF title (default from the name), author + contact (default from git config). `[4]`
- **Create a GitHub repo + push?** via `gh` — default yes. The degit left a local-only repo, so this is a real step. `[8]`
- **Generate the Pages workflow?** `task deploy-setup` drops in `.github/workflows/deploy.yml` — default yes when publishing. `[8]`
- **Custom domain, or the default `*.github.io`?** default github.io; if custom, write a `CNAME` and give the DNS records to set. `[8]`

**Defer** (don't raise unless the user does): collections (labels + order — emerges as entries accrue, §6.5), house style (`HOUSESTYLE.local.md`, extend/replace — advanced), license (ships MIT, offer to change only if asked).

**Not a choice, an instruction:** enabling Pages (*Settings → Pages → Source: GitHub Actions*) is a GitHub-UI click you can't do — tell the user to. And commits never record agent authorship (a rule, not a prompt).

0. **Prereqs.** The repo needs three CLIs: `uv`, `typst`, and `go-task`. If any are missing, **offer to install them yourself and — once the user approves — do it**; don't stop and make the user paste commands. macOS: `brew install uv typst go-task` (or install `uv` via `curl -LsSf https://astral.sh/uv/install.sh | sh`). Linux: `uv` via that same curl script; `typst` and `go-task` from their release binaries or the user's package manager. Confirm each is on PATH (`uv --version`, `typst --version`, `task --version`) before moving on.
1. **Install.** `task install` (Python deps via `uv`).
2. **Lay down the demo, then see the loop work.** The repo ships **engine-only** (a clean, empty tree — building it now would show a friendly empty-state homepage). Ask the *demo-or-clean* question first: most users learn best from a worked example, so unless they opt to start clean (bare `task scaffold` → skip to step 3), run `task add-demo-content` — it lays down the folder structure and overlays the example (the `neuron`/`mujoco` tools, `exp00*` runners + writeups, a deck). Then `task run -- exp000` (runs the tool, stages `artifacts/data/exp000/`), then start `task dev` in the background — Typst's own server with live reload. **Report the live URL to the user** (<http://localhost:3000>, or the next free port if 3000's taken — read the actual URL from `task dev`'s output, don't assume 3000). Open the exp000 page and explain in a sentence or two how the artifact became that page.
3. **Stack** (the foundational choice — settle it before anything else). Ask which language their *tools* will be written in: **Python (`uv`) by default**, or MATLAB/Julia/R/Octave. It changes what gets scaffolded and how a tool runs, so it can't wait until the first experiment. If Python, note it and move on. If not, follow [`MIGRATE-STACK.md`](MIGRATE-STACK.md) **now** to wire the language's runner glue + figure helpers, so their first experiment lands on the right stack instead of being ported later.
4. **Brand it.** In *one pass*, gather and write the optional root `demolab.yaml`: site name (default "demolab"), one-line tagline, book/PDF title (defaults from the name), author + contact (offer to pull from git config). The engine defaults any key you omit, and updates never touch it. `task dev` hot-reloads. The web theme (`style.css`) and icon (`favicon.svg`) live *inside* the black box `demolab-engine/build/`; editable, but overwritten on update — leave deeper theming as advanced for now.
5. **Confirm the scaffold is solid** — the checkpoint before any of *their* content. The structure is laid down (`writings/ experiments/ tools/ artifacts/` + `demolab.yaml`), `task build` is green (the empty-state homepage on a clean tree, or the demo site), and `task test` passes. Walk the tree with the user in a sentence so they know where things go. **Only once this is clean do you ask what to compute** — don't build a first experiment on a half-set-up tree.
6. **Scaffold their first experiment** (the point of the whole thing). *Now* ask what they want to compute — keep it small. *You* scaffold the experiment + writing pair (`experiments/expNNN.py` + `writings/expNNN.typ`) by modeling on an existing one — a working skeleton, not a stub. Then, following `../guides/RULES.md`:
   - Add the experiment's tool in its **own new** directory `tools/<their-tool>/tool.py` — *not* as a subcommand of a shipped demo tool (`neuron`/`mujoco`), because step 7 deletes those and would take the user's work with them. Model it on `tools/neuron/tool.py`: copy `setup_run_dir`/`write_output`, write `config.json`/`output.json`/the data as a CSV, pass a `manifest` with the headline metrics. **The tool emits data, not plots** — the runner renders the figure from the CSV; a *rendering* (physics video) is the one exception a tool produces itself (`headline_video`). **Add a test** `tools/<their-tool>/test_<tool>.py` and confirm `task test` passes.
   - Fill in the runner `experiments/expNNN.py` (model `exp000.py` for one tool, `exp002.py` for a mix); declare `COMMANDS`, and **render the figure(s) from the tool's CSVs** into `artifacts/data/expNNN/` (see `exp000.py`'s `plot_trace`/`plot_network`). A video tool's runner just copies the `.mp4` (see `exp002.py`).
   - Fill in the writeup `writings/expNNN.typ` as a `#let meta = (title, date, ...)` + `#let body = [ ... ]` pair, modeled on `exp000.typ`. Read the run with `#let run = json("/artifacts/data/expNNN/numbers.json")`, embed figures with `#image("/artifacts/data/expNNN/fig.png")`, and render the parameter/metric table with `#numbers-table(run.<command>, title: "…")` from `demolab-engine/build/lib.typ` — **do not hand-type numbers** (that defeats the "can't drift" guarantee). For a video, use `#video("<file>.mp4", caption: […])` (plays in HTML, omitted from the PDF).
   - Run it with `task run -- expNNN`, then `task build` (or the running `task dev`) and open the new page + its PDF with the user.
7. **Clear the shipped demo** — *only after step 6 works*, so a real example existed as a template. Run `task clear-demo-content`: it removes exactly the paths in `demolab-engine/scaffold/demo-manifest.json` (the `neuron`/`mujoco` tools, the `exp00*`/`ar00*` runners + writeups + deck, the Streamlit `playground.py`, and their staged `artifacts/`). The user's new experiment and everything in the framework zone (incl. `demolab-engine/`) aren't in that manifest, so they're untouched by construction — no hand-deleting by id. Then `task clean` and `task build` to confirm the site still builds with just their entry.
8. **Publish** (opt-in). Ask whether they want it online (default yes; if no, stop — it all works locally). If yes: create + push a GitHub repo (`gh`, ask public/private), then run `task deploy-setup` to drop in `.github/workflows/deploy.yml`, then **tell the user to enable Pages** (*Settings → Pages → Source: GitHub Actions* — the one UI click you can't do), then push. Run `task build` first to check it compiles; confirm the Actions run succeeds. The site uses relative links, so it works under any Pages path with no base config.

Notes: provenance is automatic — each run stamps its git commit into `numbers.json` and the page/PDF footer. Commit the tool code *before* a run you intend to publish, so the footer reads clean (an uncommitted run stamps *dirty*).
